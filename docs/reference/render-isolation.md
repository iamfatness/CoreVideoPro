# Windows render isolation

The experimental Windows paths for [#517](https://github.com/iamfatness/CoreVideoPro/issues/517) are selected at process launch. Both switches default off pending the installed acceptance in [render-delivery-spec.md](render-delivery-spec.md).

`COREVIDEO_ISOLATE_MONITORS=1` creates one monitor compositor on a separate D3D11 device on the Program adapter. Its immediate context, source conversions, Preview and multiview passes, and exporter creation/resize/destruction belong to its worker. Program submits immutable frame references and plans to one replaceable pending slot. An active job is never mutated. New jobs replace pending work rather than accumulating latency. Backend exceptions preserve the last result and increment a failure count.

The batch result includes the tile geometry/tally belonging to its exported frame identity. A bounded history correlates asynchronous multiview export publication with tile metadata; unknown identities do not acquire the newest labels. Frame identities describe exporter publication, not display completion. Program's multiview cell continues to sample the separate buffered Program export. A dedicated device removes CPU scheduling/context ownership coupling; it does not establish immunity to shared GPU contention or delivery-export contention.

WinUI's Program, Preview and multiview surfaces consume composites. Scene-editor layers consume CPU previews. Individual GPU source exports are requested for the compatibility Preview fallback while no composite Preview scene exists. That fallback currently permits all incoming sources because the shell can select its primary before scene synchronization. A composite Preview removes those source-export demands. Inspector/popout demand kinds are reserved in the internal request type; no new UI surface is implied.

`COREVIDEO_GPU_CAPTURE=1` adds an immutable D3D11 image to WGC frames. Capture allocates three full-resolution shared images and imports their views on registered compositor devices before publication. Each image is published only after its capture-context completion query succeeds. Render contexts sample those prepared views without a texture open, CPU upload, or keyed-mutex wait. Their preallocated read queries retain leases until GPU reads finish; CPU reference destruction alone cannot free a slot for overwrite. Exhausted leases use the existing CPU representation. GPU image residency is bounded to 512 MiB across active and retained images; capture keeps at most one retiring pool generation and defers further admission while it remains leased.

With GPU capture enabled, WGC transfers OS frames to one capture worker with one replaceable pending slot. CPU recording demand does not change the production mailbox policy. The core registers CPU demand for selected active ISO sources through both capture wrappers. Before explicit demand arrives, WGC enables the separate CPU branch for compatibility; afterward only CPU demand requests it. Normal same-adapter capture publishes a GPU image without a CPU mirror attached. CPU arrivals are drained separately through `takeCpuVideoFrames`, preserving their own frame IDs, source epochs and compositor capture times. Shell-owned camera thumbnails remain separate. Capture `droppedFrames` counts production mailbox replacement, refusal and processing exceptions, not unobserved OS losses or CPU branch loss.

GPU readiness is polled on the capture worker for up to 2 ms. Unavailable slots or pending GPU completion retain the last completed image and increment `gpuCapacityRefused` or `gpuNotReady`, also included in capture `droppedFrames`; they do not force CPU readback. Adapter mismatch, unavailable views or allocation failure can retain the established CPU fallback. That fallback still uses capture-worker readback with nonblocking Map polling bounded to 100 ms. Neither switch changes Program buffer depth or source resolution.

ISO uses a private three-image copy pool and a conversion worker with its own D3D device/context. Its device is created on the session lifecycle owner. Private pool generations are built on a separate preparation worker, with at most one preparation admitted at a time. An unready preparation refuses CPU admission explicitly while production continues. Stale/unleased generations retire on the preparation owner before allocating their replacement; admission never adds a third private generation. Conversion admits one active and one pending job in order, refusing new work at capacity instead of superseding admitted recording frames. Its completed CPU FIFO holds at most four arrivals. Private images, staging and leased CPU output buffers share the 512 MiB ingress budget; resize allows one retiring private generation. Preparation, capacity, conversion-queue, conversion-failure and completed-output refusals are counted separately and surfaced in capture warnings. `IsoVideoIngress` appends every drained identity, keeps the existing four-pending-frames-per-source oldest-eviction policy, and stamps ISO with capture time rather than delayed conversion completion. Capture time is calibrated from WGC's QPC timestamp to the core steady clock; clock uncertainty is not yet exposed. ISO arm/readiness qualification must account for initial preparation refusals rather than treating them as delivered frames.

The capture owner retains OS frames until all source copies finish. The completion fence is ended and flushed in the source-copy batch before polling the production query. Ending it after the earlier wait caused sustained retirement refusals in a real WGC regression trial on the reference rig. Idle polling retires both OS-frame leases and CPU copies even when the screen becomes static. Shutdown waits boundedly and retains uncertain leases rather than reusing them. Production/monitor pool allocation and complete resource destruction still need the specification's asynchronous lifecycle treatment; complete typed visibility demand and prepared CPU fallback uploads also remain unqualified.

WGC session creation and stop/join run on a dedicated lifecycle owner. Its command mailbox holds at most 16 source IDs and coalesces repeated requests to the newest revision. A disconnected source disappears from the poll roster immediately, even while its worker is retiring; a cancelled start cannot publish into a later reconnect. Input status distinguishes connecting, stopping and failed starts. Session creation samples the GPU feature switch from the device's launch configuration, rather than rereading mutable environment state on the worker. Final module shutdown may join the lifecycle owner. Shared frame/resource leases can outlive a retired session; GPU completion rules still apply to those leases.

WGC also creates a separate three-image pool for registered monitor devices. Monitor admission substitutes this private image and releases the production capture lease before queuing work. If neither a private GPU image nor CPU content exists, the job is refused and the last completed monitor result remains visible. The worker's `failed` count includes these admission refusals. Optional capture copies report `monitorCopied` and `monitorRefused`. Their residency has a separate 256 MiB cap, including retained generations, and permits one retiring generation per capture. This cap covers the new private ingress images; it does not yet account for all existing monitor compositor caches, export surfaces and staging allocations. Device registration currently requests copies even when a shell surface is hidden; visibility-specific demand remains unqualified.

`realtimeEvidence.monitorWorker` reports submissions, completions, superseded pending jobs, exceptions, occupancy, last sequence and last worker duration. `displayPresentationVerified` remains false. `[monitor-worker]` logs the same bounded-work counters. These counters describe monitor jobs, not receiver frames.

The asynchronous virtual-camera publisher calls the Windows publisher's direct worker entry point, avoiding a second pending-frame queue. Camera status includes process-lifetime `framesAccepted`, `pendingFramesReplaced`, and `publicationExceptions`. Difference these counters across a measurement interval. Successful backend return is not proof of receiver display. DLL read/emission diagnostics retain their separate semantics described in [virtual-camera.md](virtual-camera.md).

Native regression coverage includes a deliberately blocked monitor while Program continues composing, replacement of pending jobs, exception recovery, independent-device reads of Preview/multiview across resize, GPU-only capture pixels with zero CPU uploads, refusal to overwrite three retained capture leases, and actual Media Foundation sample bytes/PTS from the locally built camera DLL. Independent-device CPU pressure tests decode each production GPU image while conversion is deliberately blocked and verify the delayed CPU image retains its original pixels, epoch and time. The opt-in real WGC test creates a small temporary animated window and exercises GPU/ISO transitions with all three monitor images retained. The camera test redirects its mapping and log to an isolated test directory and neither registers the DLL nor restarts Frame Server. These are correctness tests; they do not replace the 30-minute/90-minute installed qualification or identify the original show's downstream camera fault.

`COREVIDEO_DELIVERY_TRACE=1` enables an optional, separately versioned camera correlation mapping. The exact buffered Program identity and delivery time travel with the immutable NV12 packet, including through pending-frame replacement. The DLL verifies mapping identity and matching seqlocks before attributing pixels, and reports the identity actually emitted for fresh/held samples. The shipping pixel ABI is unchanged. V2 log summaries preserve unknown status for missing or racing correlation and never claim receiver presentation. Tests exercise stale epochs, replaced mapping identity, queue supersession, and wrong-format input followed by correctly attributed held output.

Core readiness, Take evidence, tile freshness and source continuity recognize GPU payloads as content. The capture bus preserves their dimensions, frame identity and shared ownership through disconnect; CPU-only ISO admission still requires its CPU representation. This distinction is necessary before removing compatibility readback.

The D3D compositor selects its sampling shader and source-export dimensions
from the admitted source texture. A prepared BGRA GPU image may coexist with
the original I420 CPU planes needed by ISO; that CPU representation must not
select the YUV shader after a BGRA view has been bound. GPU-only exports use
the admitted image dimensions, even when CPU pixel dimensions are zero. If
no compatible GPU view/read lease is admitted, the existing CPU fallback
selects its own format. `PreparedSourcePixels` checks actual Program pixels
and independently consumed source-export pixels for these cases, with zero
CPU source uploads for the admitted GPU view. This format correction does
not implement off-Program CPU preparation or qualify delivery performance;
those remain under [#802](https://github.com/iamfatness/CoreVideoPro/issues/802).

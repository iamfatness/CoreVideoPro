# macOS 1.0.0 release qualification (installer 14), 2026-11-26

## Verdict: NOT QUALIFIED. No installer was built.

Gates 1 and 2 pass. Show drills (gate 3) and hardware streaming (gate 4) fail reproducibly.
Phase C was not started: no build 3100, nothing signed or notarized, no `dist/`.

Two separate problems:

1. **1080p30 streaming on the GPU-direct path has broken video timestamps.** This is the shipping
   default. It is deterministic and does not depend on load.
2. **Frames are lost intermittently**: decoded-frame delivery in the show drills, and per-frame
   delivery on some 60 fps streams.

## macOS has no Program buffer

The snapshot reports `programBuffer.status = "unsupported"` (capacity, produced and delivered all 0).
Only the D3D11 compositor implements the buffer. So on macOS:

- every `program-buffer underruns: 0` and `gpuNotReady: 0` is **vacuous**, not evidence of delivery;
- no 2 or 3 frame buffer absorbs a late render. `render.deadlineMisses` is CPU-submission lateness only,
  with no GPU-completion or presentation proof.

Presentation by the scheduled deadline is therefore **unverified** for every configuration here.

### Defect: GPU-direct 1080p30 video timestamps

- Received video PTS: 0, .033, .133, .167, .233, .333 ...: an average step of 66.7 ms for frames sent
  at 30 per second. Video reaches 67.97 s of media while audio reaches 59.69 s. The sink stopped at its
  `-t 68` media-time limit about halfway through the video in wall time, which is why the script reads
  15 fps. Video time runs at about twice audio time, so **A/V diverges by about 1 s per second**.
- The encoder muxed about 12 Mbps against a 6 Mbps target.
- Cause (from code): `VideoToolboxGpuVideoEncoder.mm:251` sets `pts = frameNumber * 10^7 / fps`.
  `frameNumber` counts 60 Hz compositor frames and `fps` is the destination's 30. `ProgramStreamClock.h`
  uses the same unit assumption.
- Why it ships: `StreamDestinations.swift` pins the RTMP, SRT and HLS rows to `fps: 30` while the canvas
  defaults to 60. **SRT and HLS at 30 fps were not tested**; the shared code suggests they are affected.
- Only on the GPU-direct path (new since installer 12). `COREVIDEO_GPU_ENCODE=0` is correct at 30 fps.
- `MediaFoundationGpuVideoEncoder.cpp:685` has the same formula. Windows behaviour is **unverified**.
- The repo script's default is 60 fps, which does not exercise this.

### SRT and HEVC at 60 fps

The frames are lost inside the core, before the muxer: muxed packet counts (SRT first run 3127, HEVC first
run 3336) match what the sink received. The cause was not found. These paths are new since installer 12,
so there is no baseline. The Mac plan's loaded-machine figures were 58.4 (h264 RTMP) and 57.9 (HEVC).
The SRT drill reached 59.4 fps with a different harness, receiver arrangement and load; the difference is
unexplained. SRT used the bundled ffmpeg as receiver (Homebrew ffmpeg has no SRT).

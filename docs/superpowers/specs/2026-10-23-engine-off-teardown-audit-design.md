# Engine-off teardown audit against the five ZoomISO rules — design

**Date:** 2026-10-23
**Status:** draft for owner review (nothing implemented; the deliverable is a document plus regression tests, not a refactor)
**Issue:** [#445](https://github.com/iamfatness/CoreVideoPro/issues/445) — backlog row T4.3 (tier 4, size S)
**Related:** `docs/reference/engine-teardown-order.md` (the 2026-07-18 G4 fixes, PR #302), `docs/reference/core-on-air-policy.md`, `docs/reference/core-restart-drill.md`, `docs/reference/realtime-isolation-audit.md`, EngineHost (#965), `docs/superpowers/specs/2026-09-23-stream-backpressure-design.md` (format reference)

## Why

The reference product (ZoomISO) froze in production on teardown. The July G4 audit (PR #302) found and fixed five defects: the engine exit path, the raw-frame callback/teardown race, the `EngineVideo` map locking, the Leave-meeting stop, and the vcam SHM delete. That audit was a one-time pass over the code as it stood on 2026-07-18, and its result lives as prose in a PR and in `engine-teardown-order.md`. Two things have changed since:

1. **The code moved.** Engine off (`zoom-stop-capture`), leave-without-killing-the-core, close-guard output stops, app-exit grace, core crash recovery (`RecoverChildAsync`), the `ZoomEngineRuntime` sender/ingest threads, and the **EngineHost** process (#965) that now owns the core and survives a WinUI crash all post-date it. `engine-teardown-order.md` itself says one gap remains ("the Zoom engine still does not get the Leave -> `stop_raw_media` order on app close") and that none of it has run against the real app.
2. **There is no written, per-rule, file:line audit.** `docs/alpha-plan.md` (G4, line 103) ticks, and `docs/beta-plan.md` (line 34) carries, "Engine-off teardown audit vs the five ZoomISO deadlock rules", but a reader cannot tell which rule was checked against which path, what evidence supported "holds", or which paths were never looked at (EngineHost did not exist).

This item produces the written audit, and one regression test per violation it finds, so the rules stop being tribal knowledge.

## The five rules

**Provenance, stated honestly.** The ZoomISO freeze log itself is not in this repository. The five rules are listed in exactly one place, `docs/alpha-plan.md:103-106` (G4), as the parenthetical "stop off the UI thread, stop-then-destroy order, no locks across SDK calls, watchdog on async stop confirm, no STA marshaling". `docs/reference/engine-teardown-order.md` (moved verbatim from CLAUDE.md, #737) elaborates rules 1-3 as hard rules with the mechanisms we chose, and `native/zoom-engine/engine/engine-video.cpp` (`~ParticipantSubscription`) cites "the ZoomISO rule" for rules 2 and 3. Rules 4 and 5 have no elaboration anywhere in the repo, so this spec fixes their wording, for the owner (who holds the original log) to correct. The wording below is the standard the audit judges against; if the owner corrects it, the affected per-rule tasks re-run against the corrected text.

| # | Rule | Precise statement | Why it froze ZoomISO / could freeze us |
|---|---|---|---|
| R1 | **Stop off the UI thread** | No code on the WinUI UI thread, or on any thread that services UI messages, may block on an SDK call, an engine IPC round trip, a process exit or kill wait, a core RPC reply, an EngineHost pipe exchange, or a thread join whose target can itself wait on any of those. Every stop rides `Task.Run` or an async path whose continuation marshals back to the UI via `UiDispatch`. "Blocking" includes `.GetAwaiter().GetResult()`, `.Wait()`, `.Result`, `WaitForExit`, `Thread.Join`, and a lock or semaphore acquisition whose holder can be blocked on the same. | A blocked UI thread cannot pump the messages the SDK is waiting on, and WinUI fail-fasts on a stuck UI (the 0xc000027b class). |
| R2 | **Stop-then-destroy order** | Teardown runs in dependency order and never in reverse: (a) leave/stop signalling, (b) raw media off and every subscription removed (`stop_raw_media`: raw recording off, `unsubscribe_all`), (c) a bounded drain so SDK completions can land, (d) renderers and helpers destroyed (`unSubscribe` before `destroyRenderer`), (e) `CleanUPSDK()` last. Nothing that holds an SDK object (renderer, helper, controller) may be destroyed after `CleanUPSDK()`, and no consumer of a producer's memory (SHM ring, frame buffer, thread) may outlive the producer's destruction. The same order applies one level up: core consumers of engine output stop before the engine process is retired. | ZoomISO destroyed renderers after stopping the SDK while a raw-data callback was still in flight. |
| R3 | **No locks across SDK calls** | No mutex, critical section or gate that an SDK callback (raw-data frame, status, participant event) can take may be held across a call into the SDK that can wait on, or synchronously invoke, that callback (`unSubscribe`, `destroyRenderer`, `Leave`, `CleanUPSDK`, `subscribe`, `SetEvent`, controller calls). Where callback and teardown must serialise, use a stopping flag plus drain, or the callback gate, never a held mutex. | The SDK may wait for an in-flight callback to return; the callback waits for our mutex; deadlock. |
| R4 | **Watchdog on async stop confirm** | Every stop whose completion is confirmed asynchronously (engine `raw_media_status` / `rawMediaActive`, the `zoom-leave` reply, close-guard output finalisation, core exit after stdin close, EngineHost `shutdown` and `detach` ACKs) has a finite deadline, a defined action when the deadline lapses (kill, give up and report, or proceed), and an outcome visible to the operator or the log. A stop that cannot be confirmed must never leave a waiter waiting forever, and the sum of nested deadlines on one path must fit inside the budget of its outermost caller (`ShutdownBudget`: 5 s timeout, 2 s core grace, 1.5 s kill wait). | ZoomISO waited on SDK stop confirmations that never came. |
| R5 | **No STA marshaling** | The Zoom SDK is called only from the thread and apartment that owns it. No code may marshal an SDK call across apartments (SendMessage, `Invoke`, a dispatcher hop, a COM proxy) and then wait for the result, and the in-process shell must not host SDK objects at all. The engine process owns the SDK on its main thread and keeps that thread's message pump alive (waits are `MsgWaitForMultipleObjects` or bounded pumped sleeps, never a blocking wait that starves the pump); other threads reach it only through the IPC command queue (fire-and-forget, never a synchronous reply wait). | A cross-apartment synchronous call into a thread that is itself blocked on teardown deadlocks both. |

Relationship to `engine-teardown-order.md`: that document remains the statement of the *mechanisms* (exit order, `m_stopping` + drain, `Task.Run` stops, the app-close flow). This spec states the *rules* those mechanisms must satisfy, and the audit's output (`docs/reference/engine-off-teardown-audit.md`) is linked from it.

A violation found here is filed as its own issue with the fix sketch; this item does not fix it.

## Audit method

For every (rule, entry point) cell:

1. **Trace**, read-only, from the entry point to the last SDK, process or OS call, naming every thread the code runs on (UI, thread pool, supervisor reader, sender, ingest, engine main STA, SDK callback thread). Record the locks held at every SDK, IPC or wait call.
2. **Classify** the cell as exactly one of `holds` (evidence file:line, and why the evidence suffices: a lock-free read, a bounded wait with its constant, a test that pins it), `violates` (offending file:line, repro idea, fix sketch), `accepted exception` (violates the letter of the rule for a stated reason, with the failure's cost and an owner sign-off line), or `N/A` (one sentence).
3. **Prove or label.** A `holds` claim rests on code, never on a comment: "ZoomISO rule" in a comment is a pointer to where to look, not evidence. Where a claim can only be shown by running the real SDK (the engine's `Leave` then `CleanUPSDK` timing, real callback reentrancy), it is labelled `read, not run` and listed in the live checklist. Per the standing rule on stability claims, nothing is called stable on the strength of a short clean run.
4. **A regression test per violation**, using an existing harness (table below). The test is written first and must be watched failing against the current code; if the harness cannot reach the violation, the finding says so and names what would. A test that documents a live violation is committed disabled/skipped with the issue number in the reason so main stays green. For `holds` cells a test is added only where the claim is not already pinned by a named existing test; the finding cites the existing test instead.
5. **No production edits.** A test seam that needs a production change is reported as a finding, not added.

## What a finding must contain

Each finding in the written audit is one block with these fields, in this order. A finding missing a field is rejected in review.

- **ID** `F-R<rule>-E<entry>-<n>` and a one-word verdict: `HOLDS`, `VIOLATES`, `ACCEPTED EXCEPTION` or `N/A`.
- **Rule and entry point** by ID and name.
- **Path**: the call chain with thread names, file:line per hop (repo-relative; valid at the audited commit, which the document names).
- **Evidence**: for `HOLDS`, the exact lines that establish it, the constant if a wait is bounded, and any existing test that pins it. For `VIOLATES`, the exact lines and the interleaving that deadlocks, hangs or loses data.
- **Repro idea** (`VIOLATES`, `ACCEPTED`): the smallest sequence that triggers it in harness terms ("fake client blocks `sendLine` for N s, then ..."), and whether it reproduces without the real SDK.
- **Fix sketch** (`VIOLATES`): what to change, in a paragraph, with its blast radius. Not code.
- **Regression test**: name, file, harness, the assertion, and "watched failing: yes / no / not reachable". For `HOLDS`: the existing test that pins it, or "none; rests on code reading" (which then also appears in the live checklist).
- **Confidence**: `read-only` (code reading), `test-proved` (a test failed on the violating code, or passes only with the guard) or `run-live` (observed on the real app or SDK). Nothing in this item is `run-live`; what needs it goes in the live checklist.

## Preliminary reading (leads, not conclusions)

Gathered while writing this spec so executors start with the right suspicion. None of it is a finding until traced and classified under the method above; some will turn out to hold.

1. **Hosted `MediaCoreSupervisor.Stop()` is synchronous over async with no token.** The hosted branch calls `_hostClient.ControlAsync("shutdown", CancellationToken.None).GetAwaiter().GetResult()`. `ControlAsync` waits on `_urgent` unbounded, `ExchangeAsync` allows a 70 s read deadline, and the host's `shutdown` runs `StopForAppExit(10 s)` before replying. If a UI-thread caller reaches it, that is an R1 and R4 breach of up to roughly 80 s. Reachability must be traced: `StudioViewModel.StopMediaCoreSession` calls `_bridge.Stop()` on the UI thread, but in hosted mode `Stop` does not raise `Health.Stopped`, so it may be latent.
2. **`StopMediaCoreSession` may re-enter itself.** `ApplyBridgeHealthChanged(Stopped)` -> `StopMediaCoreSession` -> `_bridge.Stop()` -> `StopChild` -> `RaiseHealth()` -> `OnBridgeHealthChanged` -> `UiDispatch.Run`, which runs inline when already on the UI thread -> `ApplyBridgeHealthChanged(Stopped)` again. Only `_shutdownPrepared` ends the loop. A test with a fake supervisor that raises `Stopped` on every `Stop` settles it.
3. **Engine process retirement relies on pipe EOF with a 1 s fuse.** `ZoomEngineProcessClient::terminate()` calls `closeIpc()` and then `stop()`; `stop()` only sends `quit` while the pipe is connected, which after `closeIpc()` it is not. The engine's loop breaks on EOF and runs `Leave`, `stop_raw_media("shutdown")`, a ~250 ms pump, `detach` and `CleanUPSDK`, but `stop()` waits 1000 ms and then calls `TerminateProcess`. A slow SDK means a kill inside `CleanUPSDK`, which is the R2 ordering failure by another route. It also suggests the "remaining gaps" sentence in `engine-teardown-order.md` is stale (EOF does give the ordered exit), but that is unproven either way.
4. **The engine runs `stop_raw_media` inside an SDK status callback.** The `MEETING_STATUS_ENDED` / `DISCONNECTING` case in `main.cpp` calls `stop_raw_media("meeting_left")`, reaching `EngineVideo::unsubscribe_all` (renderer `unSubscribe` / `destroyRenderer`), `StopRawRecording` and the audio `unSubscribe`, on whatever thread the SDK raised the status. The lock placement is right (maps moved out under `m_mtx`; audio callbacks do not take `m_subscribe_mtx`), but destroying renderers from inside an SDK callback is an R3/R5 question the July audit did not ask.
5. **Core `leave()` does not wait for the engine.** It enqueues `leave`, resets state and returns, and the shell then says "Disconnected from Zoom." R4 asks what bounds the *engine's* leave: the next `join()` retires the process via `stopReader()`, and app exit uses EOF. Likely `holds by design`, but the audit must name the backstop and what the operator sees if the engine never confirms.
6. **Engine-off confirmation is a bounded poll** (`StopEngineRawMediaAsync`: 12 x 250 ms, then an honest "Zoom has not confirmed raw media stopped"). Likely `holds` for R1 and R4; confirm `StopZoomCaptureAsync`'s own RPC timeout and that the unobserved task cannot fault unobserved.
7. **A hard kill ends the engine with no ordered exit.** The kill-on-close job object prevents an orphan SDK helper after a core crash, at the price of R2. Expected class: `ACCEPTED EXCEPTION` (a crash cannot run an ordered exit), with the consequence recorded (Zoom keeps showing the raw-recording indicator and a ghost participant until its server-side timeout) and an owner sign-off line. Not a defect to fix.
8. **EngineHost console exit never stops anything**, by design (`DetachHostedEngineOnExit` returns before any kill-tree fallback; `EngineHostClient.DisposeAsync` is bounded to 2 s and swallows its failures). Expected `holds` for R1 and R4; the audit must still show the 2 s bound is real (linked deadline token) and that a wedged host cannot hold the console's close beyond `ShutdownTimeout`.

## Acceptance

The item is done when all of these are true, and the PR states which claims are `read-only`:

1. `docs/reference/engine-off-teardown-audit.md` exists and contains the five rules (as in this spec, or as the owner corrects them), the audited commit SHA, the 5 x 5 rule/entry-point matrix with every cell classified, and a finding block for every cell (identical cells may share a block that names them) with all required fields.
2. Every `VIOLATES` finding has a fix sketch, a filed GitHub issue (`gh issue create`, label `backlog`), and a regression test that was watched failing (or a statement that no harness reaches it and what would). Every `ACCEPTED EXCEPTION` has an owner sign-off line left blank for the owner.
3. The suites touched pass: the native suite (Release; both the new tests and the neighbouring `ZoomEngineRuntime`, `EngineShareLifecycle`, `JsonRpcServer` filters), `CoreVideoPro.MediaCore.Tests` and `CoreVideoPro.WinUI.Tests` filtered to the new classes plus the neighbours named in the plan. A test that intentionally fails against current code is disabled with its issue number so main stays green; the finding says how to enable it.
4. `docs/BACKLOG.md` row T4.3 is updated with status, the document link and the filed issue numbers. `docs/reference/engine-teardown-order.md` gains one link line to the audit and, if finding 3 proves the "remaining gaps" sentence stale, a one-line correction pointing at the finding (documentation, not a refactor).
5. A **live checklist** section lists each `read, not run` claim and the exact rig step that would verify it (leave/rejoin cycles, exit in a meeting, EngineHost kill, a slow `CleanUPSDK`). The audit claims none of them.
6. Review confirms no production file changed outside tests, test seams and docs.

## Risks, named

- **The wording of R4 and R5 is ours, not the owner's.** Mitigation: this spec states them for review before the per-rule tasks start, and each task is parameterised on the rule text.
- **Reading is not running.** The SDK exists only in the real engine, so most R2/R3 evidence on engine code is `read-only`. The audit says so rather than upgrading it. The `EngineShareLifecycleTest` pattern gives a real mock for `EngineVideo` callbacks and is the most valuable harness addition.
- **Line numbers rot.** The audit pins a commit SHA and cites function names beside file:line; a reviewer re-runs the greps, not the numbers.
- **Scope creep into fixing.** The temptation on finding a violation is to fix it. The plan forbids it; the issue carries the fix sketch.
